## 4. Safety rules that make "no accidental deletion of staging" enforceable

1. **State separation:** staging state is `staging/platform.tfstate` in the staging bucket; production state is `production/platform.tfstate` in the production bucket. A production plan or destroy can only address resources in its own state, so it **cannot delete a staging resource**.
2. **No `terraform import`, no `-target`, no state surgery** involving staging, ever, in this plan.
3. **Every plan is checked by `prod-guard.sh`** and is rejected if it contains any `delete` or `replace` action, any non-production name, or any resource in a staging-owned state.
4. **Staging is never modified** by any step below except where this plan says so explicitly (none in sections 5–6). Specifically: staging IAM roles keep their current names and trust, even though they trust the 404 repo.
5. **Before E1 (the billing apply)** I capture a read-only staging inventory (ECS, RDS, VPC, buckets, secrets names, KMS aliases, IAM role names, CloudFront ID) and **diff it after each apply**; any difference stops the work.
6. **Local reads/writes of the staging state lock:** a staging plan takes a lockfile in the staging bucket, so I will not run staging Terraform at all in this plan (use `describe-*` calls instead).
