### Deployment approval mechanism (works without a paid GitHub plan while the repo is public)

1. **Environments, created first (F2), before any role/ARN variable exists:**
   - `production`: required reviewer `muhamedhalim`; deployment branches = **selected: `main` only**; "Allow administrators to bypass" **off**.
   - `production-db-approval`: same reviewer + `main` only.
   - (`infra-production` only if D7 later moves Terraform into CI, with the same settings.)
2. **Branch protection on `main`:** block force-pushes and deletion (free for public repos). Optional: require a pull request. That adds friction for a solo maintainer but stops a direct workflow edit from being dispatched the same minute.
3. **Two-key rule per production action:** (a) your chat approval naming the step, then (b) your click on the GitHub environment approval after reading the run's plan/diff. `workflow_dispatch` alone is **not** sufficient: anyone with write access can dispatch from any branch, the run would not pause without reviewers, and the environment-based OIDC subject would match.
4. **Known limitation:** with one maintainer, the reviewer approves their own run. GitHub's "prevent self-review" must stay **off**, or nobody could approve. This gives intent confirmation, not two-person integrity.
5. **Proof of deployment = AWS, not CI:** after every deploy, verify the service's task-definition image tag equals the expected commit, and the running tasks' `imageDigest` equals the ECR digest of that tag (H2).
